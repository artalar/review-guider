## Headline

The write engine itself is the good part. `applyGuideStep` journals `applying` before it
touches a byte, bumps `appliedIndex` and the applied ref only after a successful write,
restores stage `reviewing` on every early return, gets `git merge-file`'s argument order and
exit-code contract right, and genuinely does not advance on conflict. `renderReveal` as the
intended-state oracle works, and the additive `v: 1` token fields really are
forward-compatible. R-apply-7 (range + apply) is closed in the stat-only pass. The
`first-in-win` plus `beginApply` pair really does make a double Tab a no-op rather than two
interleaved writes.

Every serious defect is one layer up, in the *state machine around* the engine, and they share
one shape: **the session enters a state the protocol correctly put it in, and cannot get
out.** An apply conflict lands in `blocked`, an exception lands in `applying`, and nothing in
the codebase transitions out of either — while `cancelSession` refuses to run from `applying`
at all. That is the same class of defect as review 001's B2/B3/M5, in a new subsystem, and it
is why the honest reading of Phase 7's done-when checklist is that the boxes are ticked
against literal wording rather than against ADR 0004's intent ("stop, surface, retry").

Separately, the one change the Implementer made *in response to* a safety failure —
"Checkout to `headBefore` failed over dirty apply writes → discard session tree before
restore" — is B1. `git clean -fd` is the single operation plan P0-6 names as never allowed,
and it deletes user files that were deliberately never stashed.

## Blocker

### B1 — Apply Cancel runs `git clean -fd` and deletes pre-session untracked work — *open*

`src/git/isolate.ts:461-481`. `restoreFromToken` opens the apply branch with:

```ts
const reset = await tryGit(repoRoot, ['reset', '--hard', resetTarget], options)
// ...
const clean = await tryGit(repoRoot, ['clean', '-fd'], options)
```

Plan Phase 2 / P0-6 states the rule this breaks in as many words: *"On conflict: **never
force, never `checkout -f`, never `clean`.**"* The sacred suite has a passing row —
*"Untracked present, `stash.includeUntracked: false` → Left on disk, never stashed"* — whose
whole point is that those files are the user's and Tabthrough does not touch them. In apply
mode they are now deleted on the way out.

Verified. A repo with one untracked file, an apply-mode token, `restoreFromToken`:

```
PROBE C outcome = blocked verification-failed
PROBE C untracked file still on disk = false
```

`reset --hard` cannot remove an untracked file, so this is `clean -fd`. The sequence the user
experiences: Cancel → their untracked WIP is deleted → verification fails against the
after-tree (which *does* contain those files, via `add -A`) → restore blocks. Nothing is
dropped, so it is recoverable by hand out of `refs/tabthrough/after/<id>`, but "your files are
gone and the automatic restore refused" is not the sacred bar, and `-d` means untracked
*directories* go too. This is reachable in Phase 7 today — a commit-entry apply session in a
repo with untracked files and `stash.includeUntracked: false` — and in Phase 8 a dirty
working tree is the entry point, so it stops being an edge case.

There is a second half. The reset+clean runs **unconditionally, before** the
"is it already restored?" verification at line 501. `restoreFromToken`'s contract is
idempotence — its own docblock says *"Verification runs before the apply too, so re-running
after a partial failure never double-applies"*, and crash matrix §4 has a row for it. In apply
mode a retried restore now wipes the tree a previous partial restore had already put back. If
the stash entry and backup ref are gone at that point (`backup-missing`), the working tree was
the last copy.

Fix, in order of preference:

1. Do not `clean`. The session knows exactly what it created: diff the `applied` checkpoint
   tree against `base`. Remove only paths in that set, and only ones that are not in the
   pre-session capture.
2. Gate the discard on `token.mode === 'apply' && token.appliedRef !== null` **and** on the
   pre-restore verification having already failed, so a retry cannot destroy a good tree.
3. If a broad discard is genuinely needed, `git clean -fd -- <paths the session wrote>` with an
   explicit pathspec, never a bare `clean`.

Regression tests this needs: an apply Cancel row in `stash-roundtrip.test.ts` with untracked
files present under both `stash.includeUntracked` settings, and a "restore run twice" row for
apply.

### B2 — Any exception inside `applyGuideStep` wedges the session in `applying`, where Cancel refuses to run — *open*

`src/model/steps.ts:252-266` and `309-323` call `runtime.beginApply()` — which flips
`sessionStatus` to `applying` (`src/model/session.ts:429-434`) — and then
`await wrap(applyGuideStep({...}))` with no `try`/`finally`. `runtime.endApply(...)` is only
reached on the outcome branches.

`applyGuideStep` is not exception-free. Its *first* statement is `readStatus`, a `git status`
subprocess that fails when the user's own git holds `index.lock`. Further down,
`writeAppliedCheckpoint` runs `read-tree`/`add -A`/`write-tree`/`commit-tree` through `runGit`,
which throws on any non-zero exit, and `advanceStage`/`persistToken` write through the store,
which in production is `globalState.update`. None of those is wrapped.

When any of them throws, `sessionStatus` stays `applying` forever:

- `LEGAL_TRANSITIONS.applying` is `['active', 'blocked', 'error']`, and the only caller is
  `endApply`, which was skipped.
- `cancelSession` returns early on `if (status === 'restoring' || status === 'applying')`
  (`src/model/session.ts:740-741`).
- `finishSession` requires `active`.
- `tabthrough.cancel`'s enablement is `sessionOpen`, so the command is offered — and does
  nothing.

So an `index.lock` collision mid-Tab leaves a half-written working tree, a journal at stage
`applying`, and **no reachable exit short of reloading the window** so that
`checkRecoveryOnActivate` can pick the token up. That is the sacred restore becoming
unreachable, which is the one outcome ADR 0001 does not permit.

Fix: `try { ... } finally { runtime.endApply(...) }` around the apply call, with the error path
landing in `blocked` (which Cancel *can* run from) and surfacing the message. Separately,
`cancelSession`'s `applying` guard should be narrowed to "an apply is actually in flight"
(`model.applyPending()`) rather than to the status, so a stuck status cannot hide the exit.

### B3 — An apply conflict is a dead end, and the message promises otherwise — *open*

`src/model/steps.ts:285` and `334`: a conflict calls `endApply('blocked')`. Nothing in the
codebase transitions `blocked → active` — the only `sessionStatus.to('active')` calls are in
`startSession` (line 618) and `finishApplyKeep`'s blocked branch (line 703, itself broken, see
[M7](#m7--finishapplykeep-transitions-restoring--active-which-is-illegal--open)). Meanwhile:

- `beginApply` refuses unless status is `active`, so `next()`/`prev()` return `false`.
- `tabthrough.sessionActive` is false in `blocked`, so both commands are disabled *and* all six
  keybindings are inert.

And the message the user is handed is:

> `Conflict applying step onto your edits in <path>. Resolve the markers, then try again.`

There is no "try again". The only exit is Cancel, which restores the pre-session tree and
therefore discards every applied step **and the user's conflict resolution work**, which is
sitting on disk inside the markers Tabthrough just wrote. From the user's seat that is work
loss, arrived at down the path ADR 0004 D4 exists to make safe, on the risk row the register
already marks High likelihood / High impact (R-apply-1).

There is a compounding bug behind it that will surface the moment retry is wired. Retrying the
same step re-merges the *marker text* as `ours`, producing nested markers. Verified:

```
PROBE A disk after conflict = "<<<<<<< current\nexport const hello = 999\n=======\n
export const hello = 1\nexport const world = 2\n>>>>>>> intended-next\n"
PROBE A second outcome = conflict appliedIndex = -1
PROBE A disk after retry  = "<<<<<<< current\nexport const hello = 999\n=======\n
export const hello = 1\nexport const world = 2\n<<<<<<< current\n>>>>>>> intended-next\n
=======\n>>>>>>> intended-next\n"
```

Not advancing is correct and `appliedIndex` stays `-1` — the safety bar holds — but the file is
mangled a little further on every press. Note also that the `status.unmerged` refusal at the
top of `applyGuideStep` cannot catch this: these markers are plain text, invisible to
`git status`, so the guard that exists for real index conflicts does nothing for the conflicts
Tabthrough itself creates.

Fix: keep the session in `active` (or add an explicit `resolveConflict` action that
transitions `blocked → active`), record the conflicted path in the model, and refuse the retry
while that file still contains conflict markers — telling the user so, instead of merging
markers into markers. Phase 10's task 10-c ("resume apply after the user resolves the
conflict") is the full version; Phase 7 shipped the "stop" without the "then what", and the
stop is only safe if there is a way forward.

## Major

### M1 — The drift warning fires on Tabthrough's own writes — *open*

`src/git/apply.ts:180-185` and `220-224`. `driftOutsideStep` filters the dirty paths from
`git status` down to "not this step's path" — but in apply mode every previously applied step
left its file dirty relative to `base`, by design. So from step 2 onward the warning names
Tabthrough's own work. Verified:

```
PROBE B step paths = [ 'src/types.ts', 'src/service.ts' ]
PROBE B step 0 kind=applied drift=[]
PROBE B step 1 kind=applied drift=["src/types.ts"]
```

Every step after the first raises `Other files changed outside this step: src/types.ts`. ADR
0004 D4 asks to *"warn if files outside the step's path were externally dirty **since last
apply**"*, and `appliedRef` is precisely the artifact that makes "since last apply"
computable. Comparing against HEAD instead makes the P1-8 early-warning useless as shipped: a
warning that fires on every step teaches the user to ignore it, which is worse than not having
it.

Fix: diff the working tree against the `applied` checkpoint tree and report only paths that
differ there *and* fall outside the step. On the first step (no checkpoint yet) compare
against `base`.

### M2 — The `tabthrough.applyPending` context key never changes, so three keybinding guards are dead — *open*

`src/ui/status-bar.ts:46`:

```ts
useVscodeContext('tabthrough.applyPending', () => model.value?.applyPending() ?? false)
```

`useVscodeContext` re-evaluates its getter on **Vue** reactivity. The getter's only Vue
dependency is `model`, a `ShallowRef` over the `session` atom, which changes when the session
*object* is replaced — never when `applyPending` flips. `applyPending` is a Reatom computed;
reading it inside a Vue-tracked getter does not subscribe to it. So the key is computed once,
at session start, as `false`, and stays `false` for the whole session.

That makes `!tabthrough.applyPending` a no-op in all three keybindings that carry it
(`alt+]`, `alt+[`, and the apply file-scheme Tab). R-apply-5's stated mitigation — "disable
next/prev while `applyPending`" — is not wired, and the iteration log's
"R-apply-5 | Mitigated | `first-in-win` + `applyPending` context key" is describing behaviour
that does not exist. `contributions.test.ts` asserts the clause is *written*, which it is;
nothing asserts it is *live*.

This is not a data race — `beginApply` still makes the second call a no-op, and I verified that
path holds — so the practical cost is a Tab press that silently does nothing while a write is
in flight. But the guard is load-bearing in the risk register and in §9.4's manual row, so it
should work.

Fix: put the derivation in the Reatom graph and bind it the way every other key is bound —
add `export const applyPending = computed(() => session()?.applyPending() ?? false,
'ui.applyPending')` to `src/model/view.ts` and use `useAtomRef(applyPending)`.
`tabthrough.sessionMode` has the same shape and is correct only by accident, because a
session's mode is immutable.

### M3 — Apply sessions still open the read-only virtual diff, and its Tab binding has no mode or pending guard — *open*

`src/index.ts:48` calls `useReviewDocuments()` unconditionally, and `reviewViewModel`
(`src/model/view.ts:150`) is non-`null` in apply mode, so every step publishes and opens a
`vscode.diff` over two `tabthrough:` documents — *in addition to* `steps.ts` calling
`ui.openWorkspaceFile` on the real file. Two editors per step, one of which is the read-only
projection ADR 0004 D2 says apply mode replaces with *"ordinary file editors + git status"*.

The keybinding consequence is worse than the clutter. The first `tab` binding is scoped on
`resourceScheme == 'tabthrough'` with no mode clause and **no `!tabthrough.applyPending`**, so
with the virtual doc focused during an apply session, Tab fires `tabthrough.next` — an actual
disk write — from the editor that was designed to be the safe one. test-matrix §9.4 flagged
this exact ambiguity as needing a decision (*"if both exist, document which binding wins"*);
the decision was not made.

Fix: suppress the virtual documents in apply mode (gate `useReviewDocuments`, or have
`reviewViewModel` return `null` when `model.mode === 'apply'`), and add
`tabthrough.sessionMode != 'apply'` to the two `tabthrough:`-scheme bindings so the guard holds
even if a virtual doc is somehow open. Then `showStepDetail` / the status-bar click need an
apply-mode behaviour — see [m6](#m6--jumpto-and-the-status-bar-click-do-nothing-useful-in-apply-mode--open).

### M4 — The applied ref survives a verified Cancel — *open*

`finalize` (`src/git/isolate.ts:673-675`) deletes `afterRef` and `backupRef` and never
`appliedRef`. After a clean apply Cancel, `refs/tabthrough/applied/<id>` is still in the
repository.

ADR 0004 D6 permits deletion once *"Cancel/recovery **verified** restore of pre-session"* —
which is exactly the branch `finalize` runs on. The consequences are all downstream of
`listGuideRefs`, which returns everything under `refs/tabthrough` except the lock:
`orphanRefs` reports a phantom orphan after a session that ended perfectly, the "Clean Up
Backups" command has stray work to do, and every manual drill in test-matrix §6 fails its
`git for-each-ref refs/tabthrough # must print nothing` check.

`apply-commit.test.ts` does not catch it because `repo.fingerprint()` covers status and file
content, not refs.

Fix: delete `appliedRef` in `finalize`, compare-and-swapping on its recorded commit the way
the other two are, and assert `for-each-ref refs/tabthrough` is empty in the apply Cancel test.

### M5 — The heartbeat stops during `applying` and forever in `blocked`, reopening review 001's M2 — *open*

`refreshHeartbeat` (`src/model/session.ts:776-786`) refuses unless
`sessionStatus() === 'active'` **and** the stored stage is `reviewing`. Apply mode adds two
states where neither holds:

- `applying`, for the duration of a Tab write (several git subprocesses plus a temp-index
  `add -A`, which is not fast on a large repo).
- `blocked`, which after a conflict is where the session *lives* until the user cancels — see
  B3 — i.e. indefinitely.

`bindSessionHeartbeat` (`src/index.ts:107`) compounds it: `while (isSessionActive())` exits the
loop on the first transition out of `active`.

Past `HEARTBEAT_STALE_MS` (30 s), `isSessionLive` reads false, and a second window's
`checkRecoveryOnActivate` finds a recoverable token and raises *"Tabthrough did not finish
restoring your work last time."* over a live apply session — then, if accepted, applies that
session's stash and releases its lock underneath it. That is review 001's M2, closed by the
heartbeat, reopened by apply's new long-lived non-`active` states. Drill §6.2 step 5 is written
to catch it and has never been run.

Fix: beat while `sessionStatus() !== 'idle'` and not `restoring`, and accept stage `applying`
in `refreshHeartbeat`. The reason the beat was narrowed to `active` was that a read-modify-write
must not race `isolate` or `restoreFromToken` — neither of which runs during `applying` or
`blocked`, so widening to those two stages does not reintroduce that hazard.

### M6 — `IsolationHandle.token` is mutable state outside the Reatom graph, and `appliedIndex` duplicates it — *open*

`src/git/isolate.ts:290` is the one non-`readonly` field in the interface:

```ts
export interface IsolationHandle {
  readonly sessionId: string
  // ...
  /** Updated after each successful apply/revert checkpoint. */
  token: SessionToken
}
```

It is assigned from three places (`src/model/steps.ts:266`, `:323`, `src/model/session.ts:700`)
and read by `teardownSession` and `finishApplyKeep` as the token they hand to git. Meanwhile
the model keeps a *second* copy of the same number in the `appliedIndex` atom
(`src/model/steps.ts:159`, written at `:270` and `:327`).

Two problems, one Reatom and one safety. The `reatom-review` rule is *"mutable fields inside
dynamic objects should be atomized"*: nothing in the reactive graph is notified when
`handle.token` changes, so no computed can derive from the authoritative value and the UI
necessarily derives from the copy. And the authoritative value is the one recovery depends on —
if the two ever disagree (they will, the moment an error path updates one and not the other),
the atom is what the user sees and the plain field is what git is told.

Fix: hold the token in an atom (`isolationToken`) with one writer, and make `appliedIndex` a
`computed` over it. The apply actions already return the new token; they should hand it to that
atom rather than mutating a shared object.

### M7 — `finishApplyKeep` transitions `restoring → active`, which is illegal — *open*

*Phase 9 code, landed mid-review. Flagged here because it is B2's wedge shape in one line.*

`src/model/session.ts:694` moves the machine to `restoring`, then line 703 does
`sessionStatus.to('active')` on the blocked branch. `LEGAL_TRANSITIONS.restoring` is
`['idle', 'blocked', 'error']`, so this throws `IllegalTransitionError`, the action rejects,
and the session is left in `restoring` — where `cancelSession` also returns early. A Finish
whose checkpoint fails therefore has no exit either.

Fix: `to('blocked')` (Cancel is reachable from there), or add an explicit `active` edge to the
table if returning to the walk is the intended semantics — but then say so in the table rather
than in one call site.

### M8 — The suite is intermittently red with `un is not a function` — *open*

`pnpm test:ci` during this review: **4 files failed, 9 tests failed, 8 errors**, in 398 s.
The errors are all the same shape:

```
Unhandled Rejection
TypeError: un is not a function
 ❯ node_modules/@reatom/core/dist/index.js:4877:3
```

attributed to `entry-points.test.ts`, `session-lifecycle.test.ts`, and reported alongside

So this looks like cross-file interference or timeout under parallel load rather than a logic

## Minor

### m1 — A renamed file applies to the new path and leaves the old one — *open*

`resolveIntendedText` (`src/git/apply.ts:159`) reads the base blob at `file.oldPath ?? file.path`
and `applyGuideStep` writes `step.path`, with no `unlink` of `oldPath`. Applying a rename step
therefore produces *both* files, and the applied tree can never converge on the after tree.
P1-9 ("rename-aware diff steps") treats renames as a pedagogy nicety; in apply mode it is a
correctness gap. Either remove `oldPath` when a renamed file's last group lands, or emit an
honest stub for renames and say so.

### m2 — Mode-only changes are silently not applied — *open*

`file.status === 'mode-only'` has no `chmod` path, so the step advances having written text
that did not change. The sacred suite cares about the executable bit (it is in the
fingerprint); apply should either set it or stub the step the way binary files are stubbed.

### m3 — Text is round-tripped through `utf8`, with no guard — *open*

`readWorkingFile` / `writeWorkingFile` (`src/git/apply.ts:81-98`) use `readFile(…, 'utf8')` and
`writeFile(…, 'utf8')`. Any file the diff does not mark binary but that is not valid UTF-8
gets replacement characters written back — a silent corruption on a path where `isBinary` was
false. The sacred suite has a CRLF row because normalisation drift matters; apply has no
equivalent. Read and write `Buffer`, decode only when the bytes round-trip, and stub otherwise.

### m4 — Deletion is inferred from empty text — *open*

`if (nextText === '' && file.status === 'deleted') removeWorkingFile(...)`
(`src/git/apply.ts:318`). A partially revealed deletion whose remaining text happens to be
empty, and a modified file that legitimately becomes empty, are not distinguishable from a
completed deletion. Decide from the step data — "this file's last group just landed and its
status is `deleted`" — not from the resulting string.

### m5 — R-apply-6's stated test hook does not exist — *open*

The risk register's test hook reads *"Import-boundary / review checklist; no `fs.writeFile`
outside apply module"*. `test/unit/import-boundaries.test.ts` checks module specifiers per
layer and nothing else — there is no assertion about where `fs` writes live. Either add it
(`node:fs` write APIs may only be imported by `src/git/apply.ts` and `snapshot.ts`) or drop the
claim; as written the write surface is guarded by review alone, which is what the risk row was
trying to avoid.

### m6 — `jumpTo` and the status-bar click do nothing useful in apply mode — *open*

`jumpTo` returns silently when `mode === 'apply'` (`src/model/steps.ts:186-190`), which matches
ADR 0004 D5 — but the status bar's command is `showStepDetail` → `revealCurrentStep`, which
opens the `tabthrough:` diff (M3). So in apply mode the always-visible affordance either does
nothing or opens the wrong editor. Point it at `openWorkspaceFile` for the current step's path.

### m7 — The `applying` crash gate asserts a token the test wrote itself — *open*

`test/unit/apply-step.test.ts` → *"journals applying mid-write so a crash leaves a recoverable
token"* writes `{ ...token, stage: 'applying' }` into the store by hand and then asserts the
store contains it. It never calls `applyGuideStep`, so it proves `memoryStore` works and
nothing about the code under test. Plan Phase 7's test gate row is *"Journal `applying` crash
leaves recoverable token"*; this does not close it. Inject a failing `exec` (the seam exists)
so a real `applyGuideStep` dies mid-write, then assert the stored stage.

### m8 — The iteration log describes behaviour that is not in the tree — *open*

The Phase 7 entry claims *"Finish **disabled** in apply (R-apply-9)"* and
*"R-apply-5 | Mitigated | `first-in-win` + `applyPending` context key"*. Finish is now enabled
for apply (correctly — Phase 9 landed), and the context key is dead (M2). Both lines should be
corrected rather than left as the record of what shipped.

## Checked and found clean

Recording these so the next reviewer does not re-derive them.

- **Double Tab cannot interleave two writes.** `saveDocuments` is awaited *before*
  `beginApply`, so both racers can get that far, but the second `beginApply` sees status
  `applying` and returns `false` without touching disk. `withAbort('first-in-win')` on each
  action covers the same-action case. Correct as written — and untested, see T1.
- **Journal ordering is right.** `applying` is persisted before any write; `appliedIndex` and
  `appliedRef` are persisted only after a successful write or a deliberate stub advance; every
  refusal and the conflict path restore stage `reviewing` before returning. The unmerged-paths
  refusal happens *before* the stage advance, so a refusal leaves no trace.
- **Token forward compatibility.** `parseToken` defaults `mode` to `readonly`, `appliedIndex`
  to `-1` and `appliedRef` to `null`, and the stage table covers `applying` /
  `finishing-keep` / `done-kept` with `isRecoverable` correctly excluding `done-kept`. Staying
  at `v: 1` is defensible.
- **`mergeThreeWay` is correct.** `git merge-file -p <ours> <base> <theirs>` with `-L` labels
  in matching order, `code < 0` treated as an error and `code > 0` as a conflict count — which
  is `merge-file`'s documented contract, including the 127 truncation.
- **Conflict does not advance anything.** No cursor move, no `appliedIndex` bump, no applied
  ref. Asserted by `apply-step.test.ts` and independently re-verified by probe A.
- **Range + apply is refused in the stat-only pass** (`ApplyModeUnsupportedError` from
  `planIsolation`), before the pre-flight and before any mutation. R-apply-7 closed for v0.2.
- **Import boundaries hold.** `src/git/apply.ts` imports no `vscode` and no `@reatom/core`;
  `src/model` still imports no `node:`. Read, not just trusted to the test.
- **Reatom idioms in the apply path.** `next`/`prev` are `action(async)` extended
  `withAsync({ status: true })` then `withAbort('first-in-win')` — right kind, right order,
  and `{ status: true }` is what `applyPending` reads. Every boundary into git is
  `await wrap(...)`. No `context.reset()` under `src/`. No stale v3 API. Every atom, computed
  and action named, including the dynamic `session#${id}` prefixes. `applyPending` for the
  read-only branch is a `computed(() => false)` rather than a missing key, which keeps the
  session shape uniform.
- **Pre-flight disclosure is honest.** `describePreflight` states that apply writes real files,
  that Cancel restores and Finish keeps, and the confirm button reads "Isolate and Apply". The
  mode chooser's dismissal returns `null` → `throwAbort()`, and `startFailed` correctly does
  not treat an abort as an error.
- **Cancel's confirmation modal** fires only when `mode === 'apply' && appliedIndex() >= 0`,
  with "Keep reviewing" as the non-destructive answer, per ADR 0004 D6.
