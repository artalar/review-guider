# Review 007 — leftover lock sidebar userflow

Reviewer: Fable (`claude-fable-5-1-thinking-xhigh`). Scope: uncommitted working tree vs `HEAD`, leftover-lock flow. Isolation contract, same-editor live-window refusal, and the Start gate were verified; the destructive half was not gated at the moment it acts.

## Verdict

**Changes needed.** `clearStaleLock` checked liveness once, then awaited an unbounded confirm, then handed `clearAbandonedLock` a repo root and no owner. That helper re-read the lock, released whoever held it *now*, fell back to an unconditional delete, and ran `cleanupGuideRefs`. A confirm-window race could wipe a live session's lock and backup refs. `staleLock` also gated on `repoLockOwner.ready()`, so every idle `.git` refresh flipped `canStart` true. The sidebar asserted "No other window is reviewing it now", which this editor cannot know.

## Findings applied

### Reatom

- [major] Drop `ready()` gate on `staleLock`; keep last `data()`.
- [minor] `clearStaleLock` uses `withAsync()` without `{ status: true }`.
- [minor] Pre-confirm reads pass `abortVar` signal; the delete is unsignalled.

### Safety

- [blocker] Capture owner before confirm; `clearAbandonedLock(root, owner)` is CAS-only `releaseLock`; no unconditional delete; no `cleanupGuideRefs`. Re-check token, status, and owner after confirm.
- [major] Clear removes only the lock. Leftover refs stay for Clean Up Backups.
- [major] Copy hedges cross-editor/profile sessions and names the owner.

### UX / Tests / Docs

- Live and recovery refuses are both warn + `[]`.
- Distinct "lock changed" vs "cleared" notices.
- `staleLock` and `lockOwner` required on the view model.
- Confirm-window race, stale recoverable token, raw-object drill lock, gate stability, and dismiss-then-clear backup survival tests.
- test-matrix §6.2/§6.3 and reatom-model atom table updated.
