## Blocker

### B1 — The "already restored?" check now returns before HEAD is put back, so a read-only review of `HEAD` ends on a detached HEAD — *open, regression*

`src/git/isolate.ts:528-542`. F1 was asked to move the apply discard *after* the verification, and
it did — by promoting the verification to step 1 and moving the whole HEAD restore down to step 3.
The early branch then returns without ever running it:

```ts
let verification = await verifyRestored(repoRoot, expected, options)
// ...
if (verification.ok) {
  token = await persistToken(store, token)
  const dropped = await finalize(token, store, options, { dropSelector: entry?.selector ?? null })
  return { kind: 'restored', stashApplied: false, stashDropped: dropped, indexRestored: true }
}
```

`verifyRestored` compares the recomputed working tree and the status digest. Neither has any
notion of where HEAD points — `canonicalStatus` deliberately drops the branch headers *"so the
digest survives a detached HEAD in between"*. So whenever the reviewed content already equals the
pre-session content, the restore declares success while HEAD is still detached where `isolate`
put it.

That is not a corner: it is **"Review a Commit… → HEAD" with a clean working tree**, where
`checkout = afterRev = HEAD` and the status was clean before and after. Verified:

```
PROBE detached during session = true
PROBE outcome                 = restored
PROBE branch after restore    = HEAD
PROBE symbolic-ref code       = 1
```

`finalize` has already dropped the stash selector, deleted the after / backup / applied refs,
released the lock and cleared the token, so nothing will ever bring HEAD home — and the user is
told *"Review finished. Your working tree is back."* The next commit they make lands on a detached
HEAD, invisible from their branch. On `main` before this slice the HEAD restore was step 1 and ran
first, so this is a regression, in the sacred path, introduced by the fix for the sacred path.

Apply mode is currently spared only by accident: after a full walk the content matches but the
status digest does not (files read as modified against `base`), so verification fails and step 3
runs. I verified that too — apply Cancel/Finish returns to `main` correctly. The guard is
incidental, not designed.

Fix: make "already restored" mean *both* halves. Read the head position alongside the
verification and require it, keeping the discard where F1 correctly put it:

```ts
const headSettled = token.checkedOut === null
  || sameHead(await readHeadPosition(repoRoot, options), token.headBefore)
if (verification.ok && headSettled) { /* finalize */ }
```

Falling through with `verification.ok` true is safe: `discardApplyWrites` is already gated on
`token.mode === 'apply'` and would need the same `!verification.ok` gate, the checkout carries no
`-f`, and step 4 re-verifies before anything is dropped.

Regression test: the round trip with a **clean** pre-session tree, for both a commit entry and an
apply entry, asserting `symbolic-ref HEAD` — see [T1](#t1--no-round-trip-with-a-clean-pre-session-tree).

### B2 — Apply mode binds Tab in every `file` editor, so every Tab press is a disk write — *open*

`package.json` keybindings 3 and 4:

```jsonc
"when": "tabthrough.sessionActive && tabthrough.sessionMode == 'apply' && !tabthrough.applyPending && resourceScheme == 'file' && editorTextFocus && … && config.tabthrough.keybinding.useTab"
```

`resourceScheme == 'file'` is every file in the workspace, related to the review or not, and
`advance()` does not look at which editor is focused. So for the whole duration of an apply
session, in any source file, Tab applies the next guide step to disk instead of indenting. This is
what test-matrix §9.4 has a row against, in as many words: *"Apply session, normal editor, no
chord → **Ordinary Tab indent — must not be stolen globally**."* `contributions.test.ts` asserts
the clause is present, so the suite currently pins the behaviour the matrix forbids.

Two things make this worse than v0.1's Tab binding, which the Architect deliberately scoped to the
`tabthrough:` scheme precisely because a read-only document has no other use for Tab:

- The whole premise of apply mode is that **the user edits real files** (ADR 0004 D4: "current =
  on-disk bytes … + user edits"). Tab is the indent key. Every stray press is an unintended write
  to the working tree, and each write moves the guide cursor, so the recovery is not "press
  Backspace" but Shift+Tab plus a 3-way merge.
- It contradicts the instruction B3's own fix now prints: *"Resolve the markers in that file, then
  press Tab to continue."* The user has to type inside a conflicted file where Tab does not
  indent, and where a mistimed Tab re-runs the apply they are mid-way through resolving.

The widget guards (`!suggestWidgetVisible`, `!inSnippetMode`, …) do not cover plain indentation,
and `config.tabthrough.keybinding.useTab` defaults to `true`, so the steal is on by default. That
setting's own description — *"Bind Tab to the next review step while **a review document** is
focused"* — is no longer true in apply mode.

Fix, in order of preference:

1. Drop the file-scheme Tab bindings. `alt+]` / `alt+[` already work in apply mode and §9.4's
   first row expects exactly that; ADR 0004 does not require Tab on real files, and overview §7.3
   flags the file-scheme binding as insufficient on its own.
2. If Tab must stay, publish a `tabthrough.stepEditorFocused` context key (the active editor's
   path equals the current step's path) and require it, so Tab is only stolen in the one file the
   walk is about — and say so in the setting description.
3. At minimum, make the apply Tab binding opt-in with its own setting, defaulting off, and record
   the §9.4 decision in the matrix instead of leaving the row contradicted.

R-apply-8 ("file-scheme Tab steal") is registered as a risk and is not mitigated; the iteration
log's Phase 7 entry lists the binding as shipped without noting the cost.

## Major

### M1 — The drift warning still fires on every step, now naming every untracked file — *open (review 002 M1 not closed)*

`src/git/apply.ts:191-210`. F9 changed the comparison from HEAD to the `applied` checkpoint, which
is the right anchor and does stop the warning naming previously applied step paths. But the
checkpoint is built by `writeWorkingTree` — `read-tree HEAD` then **`add -A`** — so its tree
contains the repository's untracked files, and the drift check then compares that tree with
`git diff --name-only <againstRev>`, which enumerates the *index*. Any path in the checkpoint tree
that the real index does not track is reported as a deletion:

```
$ git ls-tree -r --name-only $checkpoint
a.txt
untracked.txt
$ git diff --name-only $checkpoint
untracked.txt
```

So with `tabthrough.stash.includeUntracked: false` — a supported setting whose whole point is that
those files stay on disk and are none of Tabthrough's business — every step warns about every one
of them. Verified through the model, three steps, one pre-session untracked file:

```
PROBE2 total steps = 3
PROBE2 token.appliedRef after first = refs/tabthrough/applied/entry-session
PROBE2 notifications after first = [ 'Other files changed outside this step: mine.txt' ]
PROBE2 step 1 moved = true  new notes = [ 'Other files changed outside this step: mine.txt' ]
PROBE2 step 2 moved = true  new notes = [ 'Other files changed outside this step: mine.txt' ]
```

Review 002's M1 rationale applies unchanged: *"a warning that fires on every step teaches the user
to ignore it, which is worse than not having it."* The mechanism moved; the failure mode did not.
`apply-step.test.ts`'s new drift row asserts only `not.toContain(step0.path)` with no untracked
file in the fixture, so it passes over the defect.

Fix: compare like with like. Build the current tree the same way the checkpoint was built and diff
the two trees — `writeWorkingTree(repoRoot)` then
`git diff-tree -r --name-only -z <againstTree> <currentTree>` — and drop the per-path `cat-file -e`
loop, which exists only to patch up the index/worktree mismatch this introduces.

### M2 — An exception during apply lands in `blocked`, and `blocked` has no way back to the walk — *open*

`src/model/steps.ts:299-302` and `361-363`. The `finally { runtime.endApply('blocked') }` closes
B2 correctly — I read every path, and `endApply`'s `if (peek(sessionStatus) === 'applying')` guard
makes the success and conflict branches no-ops, so the only status the `finally` can set is the
one after a throw. Cancel is reachable from there, `LEGAL_TRANSITIONS.applying` includes
`restoring`, and the journal's `applying → restoring` edge exists. The wedge is gone.

What replaces it is a one-way street. Nothing transitions `blocked → active` (the edge exists in
the table and has no caller — see [m1](#m1--endapply-is-not-owner-scoped)), `tabthrough.sessionActive`
is false in `blocked` so all six keybindings and Finish are inert, and the only exit is Cancel,
which discards the entire walk. `applyGuideStep`'s first statement is still a `git status` that
fails while the user's own git holds `index.lock` — the exact transient review 002 named — so a
half-second collision now costs the user every applied step.

The engine is better behaved than the machine here: every *handled* refusal restores stage
`reviewing` and stays `active`, and after a throw the journal is left at `applying`, which is
recoverable and heartbeat-covered. So the information needed to return to the walk exists.

Fix: distinguish "the write never started" from "the tree is in an unknown state". `readStatus`
failing before `advanceStage(store, token, 'applying')` should surface as a `refused` outcome
(`reason: 'io'`) and keep the session `active`, exactly like the other refusals; only a throw after
the first byte is written needs `blocked`. Failing that, give `blocked` an explicit
`resumeApply` action so the register's "stop, surface, retry" is true of exceptions too — Phase 10
task 10-c is the full version, and it now has a second state to resume from.

### M3 — `next` / `prev` report an abort as a business failure — *open*

`src/model/steps.ts:294-298` and `356-360`:

```ts
catch (error) {
  const message = error instanceof Error ? error.message : String(error)
  await wrap(ui.notify('warn', `Apply failed: ${message}`))
  return false
}
```

Both actions carry `withAbort('first-in-win')`, so a superseded call that has already passed an
`await wrap(...)` boundary rejects with an abort — and the user is told *"Apply failed: …"* about a
press that was correctly ignored. The `reatom-review` rule is *"do not treat abort rejections as
business errors unless the flow explicitly needs that"*, and `startFailed`
(`src/model/session.ts:508`) already does the right thing with `isAbort(error)`.

Fix: `if (isAbort(error)) throw error` before the notify, so the abort propagates and the `finally`
still runs.

### M4 — `IsolationHandle.token` is still mutable state outside the graph — *open (review 002 M6)*

`src/git/isolate.ts:289`, written from `src/model/steps.ts:267`, `:339` and
`src/model/session.ts:684`, with `appliedIndex` duplicated as an atom
(`src/model/steps.ts:159`, `:271`, `:343`). Acknowledged by the Implementer as not cheap and left
open. It is the same finding as [003 M7](./003.md#m7--isolationhandletoken-is-still-mutable-state-outside-the-graph-and-finish-is-now-a-third-writer),
which describes the concrete failure mode Finish adds; the Reatom rule is *"mutable fields inside
dynamic objects should be atomized"*. Fix once, as one `isolationToken` atom with a single writer
and `appliedIndex` as a `computed` over it — not twice, in two phases.

### M5 — The B1 discard predicate keeps pre-session untracked files but still deletes files the user authored mid-walk — *open, and Phase 8 inherits it*

`src/git/isolate.ts:491-493`. The half review 002 B1 asked for is done and I verified it end to end
through the model, with `stash.includeUntracked: false`, a pre-session untracked file, and a step
that adds a new file:

```
PROBE mine.txt after cancel   = true
PROBE new.ts after cancel     = true      (tracked at headBefore after the restore — correct)
PROBE branch after cancel     = main
PROBE fingerprint equal       = true
```

No bare `clean`, the discard runs only after verification has already failed, and the sacred
fingerprint holds. That closes B1 as written.

What is not done is the other half of review 002's own fix list — *"Remove only paths in that
[session-written] set"*. The shipped predicate is `headPaths.has(path) || !afterPaths.has(path)`,
whose second clause means "absent from the pre-session capture", i.e. **anything new**, including
files the user created during the walk. [003 M1 / B2](./003.md#m1--discardapplywrites-deletes-untracked-files-the-user-authored-during-the-walk)
verified the deletion and owns the fix; recorded here because it is the F1 predicate, because
Phase 8's dirty-tree entry inherits it, and because on the `deactivate` path there is no
confirmation at all. On the explicit Cancel path the modal does say *"discards applied steps and
mid-walk edits"*, which is disclosure of a sort — but a `clean -fd` of a path the session never
wrote is still the operation P0-6 names, and "stop and explain" beats "delete and verify".

## Minor

### m1 — `endApply` is not owner-scoped

`sessionRuntime().endApply` guards on the *status*, not on who started the apply, so the
`finally` of one action can act on another action's `applying`. Between `endApply('active')` and
the `finally`, `next` still awaits `notify` and `openWorkspaceFile`, so a `prev` started in that
window would be forced to `blocked` mid-write. It is unreachable today only because `advance()`
and `retreat()` (`src/commands/index.ts:82`, `:106`) both return early on
`model.applyPending()` — a UI-layer guard standing in for a model invariant. Give `beginApply` a
token that `endApply` must present, or move `endApply` above the trailing awaits.

### m2 — `tabthrough.next` / `tabthrough.previous` enablement omits `!tabthrough.applyPending`

`package.json` gates both on `tabthrough.sessionActive` alone, so the palette offers them during
an in-flight write. Harmless because of m1's command-layer guard, but test-matrix §9.4's *"Pending
apply → Next/Previous disabled or no-op"* resolves to "no-op" for the palette while the
keybindings say "disabled". Now that the key is live (F7), the enablement should use it.

### m3 — Review 002's m1–m5 and m7 are all still open

Renames leaving both paths, mode-only steps silently not applied, UTF-8 round-tripping without a
guard, deletion inferred from empty text, R-apply-6's missing write-surface import assertion, and
the `applying` crash-gate test that writes the token it then asserts. Correctly deferred by the
Implementer; listed so the count stays honest. m7 is worse than "not done": `steps.ts` never
passes `exec` to `applyGuideStep`, so the injection seam the fix needs does not reach the model —
see [T2](#t2--no-injected-mid-write-throw).

### m4 — The sacred suite's "restore twice" row skips the path it is named for

`test/integration/stash-roundtrip.test.ts:518-531` re-seeds the retry token with
`afterCommit: null, afterTree: null`, which takes the "nothing was ever captured" shortcut at the
top of `restoreFromToken`. The row B1's second half was about — a retry that reaches the discard
with a tree a previous partial restore already put back — is not exercised. Drive a `blocked`
outcome first (a foreign edit to the same file), restore the tree by hand, then retry.

### m5 — Nothing tests `ui.applyPending`

F7's fix is correct as read: `applyPending` is a real `computed` over `session()?.applyPending()`
and `useAtomRef` subscribes it, so the context key tracks `next.status().isPending` — which is
available because both actions carry `withAsync({ status: true })`. But `view.test.ts` has no case
for it, and the failure mode F7 fixed (a key that is computed once and never again) is exactly the
kind that a unit test catches and a reading does not. Three lines: start an apply session, assert
`false`, hold a pending apply, assert `true`.

### m6 — `fileParallelism: false` is a mitigation, and the bill is 435 s

F3's diagnosis is right — `context.reset()` in `beforeEach` aborting another file's in-flight
`take()` is what produced `un is not a function`, and serialising removes the race. The suite is
green and deterministic across my run, so M8 is closed. But `context.reset()` is still called
between tests *within* a file, the root cause is untouched, and a merge-blocking suite that takes
7¼ minutes will only grow. The Architect's own rule for `src/` — scope with `context.start`
instead — is the fix that would let parallelism come back.

## Test gaps

### T1 — No round trip with a clean pre-session tree

verification always fails and the HEAD restore always runs. The clean-tree case — the most common
way anyone reviews a commit — has no coverage, which is why [B1](#b1--the-already-restored-check-now-returns-before-head-is-put-back-so-a-read-only-review-of-head-ends-on-a-detached-head--open-regression)
shipped green. Add it for a commit entry and an apply entry, asserting `symbolic-ref --quiet HEAD`
succeeds and names the original branch. This is the highest-value missing test in the project right
now: two lines, and it fails today.

### T2 — No injected mid-write throw

Review 002's m7 asked for a real `applyGuideStep` failure. `ApplyStepArgs` has an `exec` seam, but
`src/model/steps.ts` never passes one, so the model cannot be driven into the `finally`. The new
`apply-commit.test.ts` B2 row sets `sessionStatus.to('applying')` by hand — it proves the Cancel
guard, which is worth proving, and nothing about `finally { endApply }`. Thread `exec` through
`SessionRuntime` (it already carries `ports`) and fail the first `git status`.

### T3 — Drift with an untracked file present

The new drift row has no untracked file in the fixture, so [M1](#m1--the-drift-warning-still-fires-on-every-step-now-naming-every-untracked-file--open-review-002-m1-not-closed)
passes through it. Assert `driftPaths` is empty across two steps with an untracked file on disk
under both `includeUntracked` settings.

### T4 — §9.1 rows still missing

Unchanged from review 002's T1 except where noted: edit-then-Tab **clean** through the model
(R-apply-1's primary row, and the only one that proves the product's central promise), unsaved
buffer refusal (the harness port always returns `ok`), double-Tab while pending, and stub / binary
apply. The conflict, marker-refuse, revert, drift and Cancel rows are now covered.

### T5 — §9.4 is now decidable and still unrun

`!tabthrough.applyPending` is live, so the pending row can finally be falsified with a keyboard.
The Tab row cannot wait for that: [B2](#b2--apply-mode-binds-tab-in-every-file-editor-so-every-tab-press-is-a-disk-write--open)
is a design decision the matrix already made and the code contradicts.
