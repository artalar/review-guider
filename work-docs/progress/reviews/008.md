## Blocker

### B1 — Finish awaits the untracked pick unguarded; Cancel (or a terminal abort) in that window makes the resumed Finish amend the user's branch HEAD with their WIP

`src/model/session.ts` `finishSession`: `readStatus` → `await pickUntracked(...)` →
`peekSidecarFinish` → `pauseOwnership.set(true)` → `runFinishRebase(...)`. The pick is an
unbounded `showQuickPick` (`ignoreFocusOut: true`), and nothing after it re-checks that the
session it started in still exists. `cancelSession` is a different action, so
`withAbort('first-in-win')` on Finish does not fire; the Cancel command stays enabled while the
pick is open.

Verified through the model — dirty `HEAD~2` review (`app.ts = wip`, untracked `notes.txt`),
`finishSession()` parked on a deferred `pickUntracked`, then `cancelSession('cancel')`, then the
pick resolved with `[]`:

```
PROBE1 HEAD after cancel   = 0963025…  (before: 0963025…)   ← Cancel aborted correctly, WIP back
PROBE1 status after cancel = M app.ts
PROBE1 HEAD after finish   = f1f7fb4…  subject = fourth  HEAD:app.ts = wip
PROBE1 status after finish = ?? notes.txt
PROBE1 notes = [ 'Review cancelled.', 'fatal: no rebase in progress' ]
PROBE1 HEAD unchanged = false
```

The abort restored the branch and popped the autostash; the resumed Finish then ran `git add -u`
and `git commit --amend --no-edit` against `fourth` — the user's real tip — folded the WIP into
it, and only then failed on `rebase --continue`. The user reads "Review cancelled." followed by a
`fatal:` about a rebase they never saw, and their working changes are gone from the tree and
inside a rewritten commit. The terminal-`--abort` + ownership-watch variant is the same path with
`reason: 'ownership'`. This is the confirm-window race of [review 007](./007.md) B1 again, one
phase later.

Fix, all in `finishSession`:

1. After **every** await that precedes `runFinishRebase` (the pick, `peekSidecarFinish`), require
   `peek(sessionStatus) === 'active' && peek(session) === model && peek(rebaseOwnership) !== null`;
   otherwise return silently — the teardown that ran already told the user what happened.
2. Immediately before running, re-read the truth: `readOwnership(model.repoRoot, owned.after,
   owned.origHead)` must be `ours`. If not, notify `OWNERSHIP_LOST` and return. This is one
   `rev-parse --git-path` + three file reads; it is not a second isolation protocol, it is the
   D5 ownership rule applied at the moment it matters.
3. Set `pauseOwnership` only after those checks pass, inside `try { … } finally
   { pauseOwnership.set(false) }` (see [m1](#m1--pauseownership-is-never-reset-when-runfinishrebase-throws)).

Regression test: [T1](#t1--finishcancel-race-through-the-model).

### B2 — A merge commit as `after` (or any todo without a `pick <after>` line) rewrites the branch on Start and reports success

`isAncestor(after, HEAD)` is the only applicability check (`startPreview`, `startSession`). For a
merge commit it is true, `planIsolation` picks `base = after^1`, and `git rebase -i` without
`--rebase-merges` linearises `base..HEAD` and **drops the merge itself** — so the todo has no
line for `after`, the sequence editor rewrites nothing, and the rebase runs to completion. Git
exits 0, `startSession` treats `code === 0` as "stopped at `after`", sets `rebaseOwnership`, and
goes `active` in `rebase` mode with `editHereEnabled` true while the disk holds the *rewritten
HEAD*, not `after`.

Verified with the shipped `dist/sequence-editor.cjs` and then through the model:

```
== before ==                              == after (REBASE_EXIT=0) ==
* 60d5491 above2                          * 76b2c12 above2
* 5ab36e0 above1                          * 9335a9f above1
*   107e27a merge side                    * 3a691ba side2
|\                                        * fab0f24 side1
| * c32f36f side2                         * 778f5f0 main2
| * 5bd5f5d side1                         * be28add base
* | 778f5f0 main2
|/
* be28add base
rebase-merge exists: no    HEAD changed: yes

PROBE5 preview startEnabled = true  rebaseApplicable = true
PROBE5 status = active  mode = rebase
PROBE5 rebase in progress = false  HEAD changed = true
PROBE5 status after watch = idle
PROBE5 notes = [ 'The rebase is no longer stopped at the reviewed commit.' ]
```

The merge is gone from the branch, the four commits above have new shas, and the only thing the
user hears — one `gitState` tick later — is that the rebase "is no longer stopped at the reviewed
commit", which implies *they* did something. The same hole covers a merge *between* `after` and
`HEAD` (the user merged `main` into the feature branch after the reviewed commit: Finish's
`--continue` flattens it) and, with `rebase.autoSquash=true`, a `fixup!` targeting a commit at or
below `after` (reordered ahead of the stop, so the picks before `after` are no longer
fast-forwards). ADR 0005 D2 defines the mode as "a stopped interactive rebase … the working tree
is exactly `after`"; here neither holds and Tabthrough says Start succeeded.

Fix, two halves, both cheap:

1. **Pre-flight, in `startPreview` and `startSession`:** rebase is applicable only when
   `isAncestor` holds **and** `git rev-parse --verify --quiet <after>^2` fails **and**
   `git rev-list --merges --count <base>..HEAD` is `0`. Otherwise `rebaseApplicable = false`
   with a hint that names the reason ("This commit is a merge — start in Worktree mode" /
   "There is a merge above this commit — start in Worktree mode"). This is the D2 rule
   "rebase cannot put the working tree at a commit that is not on the current branch" applied
   to the case where it cannot put it there *as a stop*.
2. **Post-start, in `startSession`:** after `startRebase` returns 0, `readOwnership(repoRoot,
   plan.afterRev, origHead)` must be `ours` **before** `rebaseOwnership.set(...)`. If it is not
   and a rebase is in progress, `rebaseAbort` and throw a `RebaseNotApplicableError` with git's
   output. If no rebase is in progress (git ran through), do not touch anything — throw with a
   message that says the rebase completed instead of stopping and names `ORIG_HEAD` so the user
   can decide. Never run the reset for them (P0-6, ADR 0005 D5 "never run").

Regression test: [T2](#t2--merge-as-after-and-merges-above-through-the-model).

## Major

### M1 — An autostash that conflicts on `--continue` exits 0, so Finish says "Review finished." over `UU` paths and a live stash

`git rebase --continue` replays, then applies the autostash; when the pop conflicts git prints
*"Applying autostash resulted in conflicts. Your changes are safe in the stash."* to stderr and
**exits 0**. `finishRebase` returns `ok: true`, `finishSession` tears down with `reason: 'finish'`,
and the stderr goes only to the output channel. Verified through the model (WIP on `note.ts`,
Edit-here change to `note.ts` amended, `third` replays cleanly, pop conflicts):

```
PROBE7 status     = idle
PROBE7 git status = UU note.ts
PROBE7 stash list = stash@{0}: autostash
PROBE7 notes      = [ 'info: Review finished.' ]
```

ADR 0005 D2 names this exact message under "Errors — forwarded verbatim" and D5 gives it a sidebar
row with Pop / Show. The row exists; the notice contradicts it. The user's WIP is in a stash and
the file has markers, and the toast says done.

Fix: on the `ok` path, if `continued.stderr` (or stdout) is non-empty, forward it in the closing
notice at `warn` level — `reportGit` already does exactly this for the banner buttons; reuse it.
Alternatively read `gitState` after and warn when `autostashes.length > 0 || conflicts.length > 0`.

### M2 — The "Will run:" line is not the command Start runs

D6 replaced the modal with the line: *"Confirmation is the Start click."* Three cases where the
line and the argv differ:

1. **Range entry.** `startPreview` computes `base = resolveCommit(`${after}^`)`; `planIsolation`
   (what `startSession` uses) computes `base = merge-base(from, to)`. Verified:
   ```
   PROBE2 preview willRun = git rebase -i --autostash --no-verify --no-gpg-sign c16f79d53453
   PROBE2 plan base       = 8e6ca800b4e7   (c3^ = c16f79d53453)
   PROBE2 match = false
   ```
   The user confirms a rebase onto `to^` and gets one onto the merge-base, which rewrites more
   commits than the line implied.
2. **Guide `defaults.finish`.** `startPreview` calls `resolveFinishPolicy(undefined, …)` — the
   guide is never read — while `startSession` reads it via `peekSidecarFinish`. A guide that
   sets `hooks: true` makes the line show `--no-verify` and the command omit it; the reverse for
   a user with `finish.hooks: true` and a guide that says `false`. The test-matrix row "Guide
   `defaults.finish` overrides the setting in both directions" is only covered at the pure
   `resolveFinishPolicy` level.
3. **Root commit.** `base = resolveCommit(after^) ?? after` shows `rebase -i <after>` while
   `planIsolation` uses the empty tree. Git refuses either way; the line is still wrong.

Fix: derive the preview from the same functions Start uses. `planIsolation` is stat-only and
already returns `baseRev`; `peekSidecarFinish` takes `(repoRoot, baseRev, afterRev)`. Call both
in `startPreview`, and drop the parallel `resolveCommit(after^)` path. Then [T5](#t5--will-run-fidelity)
pins the two argvs to each other.

### M3 — Finish does not save dirty editors before `add -u`

`startSession` calls `saveDocuments(repoRoot, [])` for rebase mode and refuses with *"Save … before
starting"*. `finishSession` does not: it goes straight to `readStatus` → `add -u`. An Edit-here
fix left unsaved is not amended; the replay then rewrites the file on disk under a dirty buffer
whose content is `after + edit` without the replayed commits' changes. VS Code shows the buffer as
dirty; saving it reverts the replayed changes in that file. The one editing surface the ADR allows
(D4) is the one Finish forgets.

Fix: the same `saveDocuments` call and refusal at the top of the rebase branch of `finishSession`.

### M4 — Cancel during `starting` SIGKILLs `git rebase -i` mid-write

`startSession` passes `options: { signal }` — the `withAbort` controller — to `startRebase`.
`cancelSession` in `starting` calls `startSession.abort()`, and `execGit`'s `onAbort` does
`child.kill('SIGKILL')`. A rebase that is still writing `rebase-merge/`, creating the autostash
or checking out `after` is killed without cleanup. `rebaseOwnership` is set only after
`started.code === 0`, so `startFailed` sees `owned === null` and runs no `--abort`. The user is
left with whatever git had written; the sidebar banner may or may not show a rebase depending on
how far git got. ADR 0005 D2's "Tabthrough does not retry, resolve, or clean up on the user's
behalf" presumes Tabthrough also does not *interrupt* git.

Fix: run `startRebase` without the abort signal (it has its own 120 s timeout). After it returns,
if `peek(cancelledStartAttempt) === attempt`, run `rebaseAbort` (git's own cleanup) and
`throwAbort()`. The read-only probes before it can keep the signal.

## Minor

### m1 — `pauseOwnership` is never reset when `runFinishRebase` throws

`GitTimeoutError` (120 s) or `GitMissingError` rejects past `pauseOwnership.set(true)`; the
session stays `active` with the ownership watch disabled until Cancel. `try/finally`, folded into
B1's fix.

### m2 — `--abort` results are logged, never shown

`teardownSession` and `startFailed` call `rebaseAbort` and only `logGit` the result. A terminal
`--continue` that raced the watch makes Cancel's abort exit 128 ("no rebase in progress") and the
user still reads "Review cancelled." — true of the review, false of the rebase. Route both through
`reportGit` (or forward when `code !== 0`).

### m3 — The replay-conflict path says "Review finished." first

`finishSession` → `kind === 'conflict'` → `teardownSession({ reason: 'finish' })` → *"Review
finished."* → then the git error. The first notice is wrong; the second is right. Add a
`CancelReason` (or a `describeClosed` variant) for "stopped on a conflict — resolve, then
Continue in the sidebar".

### m4 — `startRebase` does not set `GIT_EDITOR=true`

`finishRebase`'s `--continue` and `state.ts`'s `continueRebase` do. With `rebase.autoSquash=true`
a `squash` line reached before the stop opens `core.editor` — for a VS Code user that is `code
--wait` — and the start hangs until the 120 s timeout SIGKILLs it (M4's failure mode without a
Cancel). Set it on Start too.

### m5 — Start-line dirty count, and what `--autostash` gives back

`state.staged + state.unstaged` counts a file that is both staged and unstaged twice (named by
the Implementer). Use the union of paths. Separately, verified: a **staged** change parked by
`--autostash` comes back **unstaged** after Finish or Cancel (`git stash apply` without `--index`
is what git's autostash does). That is git's behaviour, not Tabthrough's, but the done-when says
"returns HEAD and WIP exactly" and the product edge table says "WIP parked … pops". Say it in the
Start notes when `staged > 0` and in the edge row; add [T7](#t7--staged-wip-round-trip).

### m6 — Retry-without-hooks re-runs the whole Finish, and classifies too eagerly

`classifyFinishFailure` returns `hooks-or-sign` for *any* non-conflict failure of `commit` or
`rebase --continue` whenever `policy.hooks || policy.sign`. The Retry then calls
`runFinishRebase` from the top — `add -u`, `add -- <ticked>`, `--amend` — against whatever state
the failed `--continue` left. `--continue` cannot fail on a hook (picks do not run `pre-commit`;
`pre-rebase` is start-only), so the retry should be offered only when the **amend** failed, and
should re-run only the amend + `--continue`.

### m7 — Sequence-editor quoting and the `.ts` dev hack

`GIT_SEQUENCE_EDITOR` is run by git through `sh -c`; `quoteArg` double-quotes on whitespace and
`"` but leaves `$`, backtick and `\` alone. Cursor's helper path (`… Cursor Helper (Plugin) …`)
is fine today; a `$` in a username is not. Escape those four inside the quotes. And
`sequenceEditorArgs: editor.endsWith('.ts') ? ['--experimental-strip-types'] : []` in
`startSession` is test scaffolding in production code — move it to the harness.

## Reatom

Nothing at Critical or High. Every atom, computed and action is named; `withAsync` precedes
`withAbort` on `startSession` / `finishSession` / `cancelSession`; every git and port boundary is
`await wrap(...)`; there are no bare `wrap(() => …)` statements and no wrapped IIFEs;
`startPreview` is a `withAsyncData` computed that reads `gitCapability()` and `gitState()` before
its first await; `willRun` is a `computed`, not a synchronised atom; abort rejections are not
reported as errors anywhere in the new code. `syncRebaseOwnership` has no `withAbort`, but
`teardownSession` flips to `finishing` synchronously before its first await, so a second run in
the same tick returns on the status check — safe.

- [Low] `connectOwnershipWatch` is `gitState.data.subscribe(() => { void syncRebaseOwnership() })`.
  Started at the activation boundary and unsubscribed on dispose, which is the recommended
  lifetime; an `effect(() => { gitState.data(); void syncRebaseOwnership() },
  'session.ownershipWatch')` would say the same thing in the model's own vocabulary.
- [Low] `pauseOwnership` is `atom(false)`; `reatomBoolean` is the idiom. `rebaseOwnership`,
  `pauseOwnership`, `inflightWillRun` are sibling atoms rather than grouped on the session —
  acceptable, since they must exist before `session#<id>` does.
- [Low] `peekSidecarFinish` reads like Reatom's `peek`; it is async IO (`git show`). `readSidecarFinish`.
- [Low] `startFailed` aborts with `peek(workspaceRoot)` rather than the `repoRoot` Start probed;
  git resolves from a subdirectory, so it works, but pass the root in `StartFailure`.
- [Low] `startPreview` runs five unsignalled git reads on every `gitWatchToken` bump while an
  entry is pending. Fine at this size; note it if the sidebar ever feels laggy.
