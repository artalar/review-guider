Scope: `src/` at `cursor/guide-reviewer-33d9`, against the `reatom-review` skill,
[reatom-model.md §12](../../architecture/reatom-model.md), [product.md](../../specs/product.md)
UX principles and P0 edge budget, and ADRs [0001](../../decisions/0001-mvp-scope.md) /
[0002](../../decisions/0002-architecture.md).

`pnpm lint && typecheck && test:ci` green at the start of the review (418 tests) and at the
end (423). Everything marked **fixed** below is covered by a test that fails without the fix.
Three commits during the review — `12adf0c`, `6036e69`, `8177522` — and one after it,
`80752e7`, which closed the three majors the review left open (M1, M2, M3) and took the suite
to 436.

**Headline.** The safety protocol in `src/git` is the strongest part of this codebase and I
found nothing wrong with the apply → verify → drop order, the journal, or the crash matrix.
The defects are all one layer up, in `src/model/session.ts`: the state machine did not always
come back from the states the protocol correctly put it in, and one gate in front of `git
stash push` was reading a probe that is only refreshed when the workspace folder changes.
Two findings were left open and both were about a *second window*, which no test and no drill
reached — those are closed now, by a per-session lock value and a liveness heartbeat on the
token; the automated tests reach the second window, the manual drill (§6.2) still needs a
human.

## Blocker

### B1 — Start stashed straight over an in-progress merge — **fixed** (`6036e69`)

`src/model/session.ts:83` — `gitCapability` is a `computed` whose only dependency is
`workspaceRoot()`. Per the Reatom reference, *"computed without dependencies will be never
reevaluated"*: it is probed once when the folder opens and never again. The comment on
`bindGitWatcher` in `src/index.ts:77` claims "the probes recompute themselves", but only
`repoStatus` reads `gitWatchToken`.

So a merge or rebase begun after the window opened still read `ok`, and nothing downstream
caught it. `planIsolation` reads `status.unmerged` and does not refuse it; `isolate` went on
to `git stash push` over `MERGE_HEAD`. The new test in
`test/integration/session-lifecycle.test.ts` starts a real conflicted merge after activation
and, before the fix, **the session opened on top of it** — no error, no refusal.

This is P2 row *"live rebase / interactive rebase in progress → refuse start"* in the edge
budget, and the README already promises the refusal.

Fix applied: `startSession` probes for itself instead of reading the cache. That is the last
gate before a mutation and the one place worth paying for extra subprocesses. The computed
stays lazy deliberately — see M1.

### B2 — A restore that finally worked left the session unusable — **fixed** (`12adf0c`)

`src/model/session.ts` `recoverBackup` — on `outcome.kind === 'restored'` it cleared
`restoreBlock` but left `sessionStatus` at `blocked` and left `isolation` and `session`
populated. `canStart` is `gitUsable() && !recoveryPending() && sessionStatus() === 'idle'`,
so a user whose files had just been put back correctly still had Start disabled, with no
command able to clear it short of reloading the window.

Fix applied: the machine returns to `idle` and drops the session it just finished restoring.
Regression test: *"returns a blocked session to idle once the restore finally verifies"*.

### B3 — Cancel during an in-flight Finish ran a second `git stash apply` — **fixed** (`12adf0c`)

`finishSession` and `cancelSession` are separate actions, so their `withAbort('first-in-win')`
guards cannot see each other; both call `teardownSession`, and `teardownSession` deliberately
passes no signal because an interrupted `git stash apply` is unsurvivable. Two applies against
one stash entry is precisely the outcome the protocol is built to avoid.

Fix applied: `cancelSession` returns early while `sessionStatus` is `restoring`.

Worth a second opinion on the shape: a status check is the cheap fix, but the durable one is a
single `teardown` action that both commands call, so one `first-in-win` guard covers both.

### B4 — The VSIX shipped someone else's copyright — **fixed** (`8177522`)

`LICENSE.md` still carried `Copyright (c) 2022 Anthony Fu`, from the reactive-vscode template.
`vsce package` includes `LICENSE.md` verbatim (verified by running it), so this would have
shipped under `publisher: artalar`. Changed to the repository owner — **please confirm the
attribution is the one you want**, since it is the one finding here I cannot verify from the
code.

## Major

### M1 — The UI still gates on a probe that never refreshes — **fixed** (`80752e7`)

B1 closed the dangerous path but not the honest one. `gitUsable`, `canStart` and
`startBlockedReason` all read `gitCapability.data()`, which is still the activation-time
answer. Start a rebase and Start still *looks* available; you now get a correct refusal when
you click it instead of a stash on top of `MERGE_HEAD`, which is the right failure mode but
not the right UI.

I deliberately did not make `gitCapability` a dependant of `gitWatchToken`: during isolation
the extension is itself writing refs under `.git/`, so every write would trigger a re-probe
(~6 subprocesses each) over the top of the last.

Suggested fix: `retryComputed(gitCapability)` driven from the watcher, debounced, and only
while `sessionStatus() === 'idle'` — the states where a stale answer actually misleads
someone are exactly the states where nothing is being written. Alternatively make the
watch-token read conditional inside the computed on the same idle check.

Fix applied: the second one. `gitCapability` reads `gitWatchToken()` only when
`sessionStatus()` is `idle`, both reads hoisted above the first await per W5. Reading
`sessionStatus` reactively is what lets the dependency come back when a session ends — a
computed that dropped its last dependency would never be reevaluated again. The cost is one
re-probe per status transition (five over a session's life) instead of one per ref write
during isolation. Regression test: *"disables Start as soon as a merge begins, with no folder
change"*, which bumps the watch token the way the bridge's watcher does. `startSession` still
probes for itself — a watcher event is not instantaneous and that is the last gate before a
mutation.

The probes moved below the state machine in `session.ts` so the computed can name
`sessionStatus` without a forward reference.

### M2 — A second window offers to "restore" the first window's live session — **fixed** (`80752e7`)

`isRecoverable` (`src/git/journal.ts`) is true at stage `reviewing`, and the journal lives in
`globalState`, which is shared across windows on purpose (ADR 0002 D3, so a second window can
see it). Nothing in the recovery path asks whether the session is still *running* somewhere.

Open a second window on a repository that window A is reviewing: B activates,
`checkRecoveryOnActivate` finds A's live token, and B shows the modal *"Guide Reviewer did not
finish restoring your work last time."* Accepting it runs `restoreFromToken` on A's token —
applying A's stash into the tree, dropping the entry, deleting both refs, and releasing the
lock — while A is still mid-review.

To be accurate about the damage: the files do come back, and A's later Finish verifies against
a tree that now matches its capture, so this is not straightforward data loss. What the user
gets is a false alarm about losing work, and a review whose isolation silently ends underneath
it. If they then edit anything before A finishes, A lands in `blocked` with `backup-missing`.

This is the hole in P0 edge row 8 (*multiple concurrent sessions*). The automated test covers
one process and drill §6.2 covers the second **Start** being refused; neither covers the second
window's **recovery** path.

There is no clean local fix — from git state alone, "crashed" and "live in another window" look
identical — so I left it. The cheapest honest design is a liveness marker: have the owning
window refresh a timestamp on the token (or on a `refs/guide-reviewer/heartbeat` ref) while a
session is open, and have `checkRecoveryOnActivate` stay silent while that marker is fresh,
falling back to the current prompt once it goes stale. Pair it with M3.

Fix applied: the marker, on the token rather than on a ref — the token is already read on the
path that needed the answer, and a ref would have been a sixth artifact to clean up.
`SessionToken.heartbeatAt` is stamped by `isolate` (again at `reviewing`, so a slow isolation
is not born stale) and rewritten every 7 s by the owning window while `sessionStatus` is
`active`. `isSessionLive` is true for any recoverable stage with a heartbeat under 30 s old —
deliberately wider than `reviewing`, because a second window that catches the first
mid-isolation is the most dangerous one to race. `recoverBackup` and
`checkRecoveryOnActivate` both refuse on it and say *"A Guide Reviewer session is active in
another window"*; `startBlockedReason` says the same instead of the false alarm about work to
restore. Regression tests: *"does not offer to restore a session that is live in another
window"* (which asserts window A's stash, refs and token are all still there) and *"offers the
crash-recovery modal again once the heartbeat goes stale"*.

Two things worth a second opinion. The beat runs only while `active`: in `stashing` and
`restoring` the journal belongs to `isolate` and `restoreFromToken`, and a read-modify-write
racing either of those could roll a stage back — a worse bug than the one being fixed. The
consequence is that a session which spends longer than 30 s isolating is briefly
indistinguishable from a crash, narrowed but not closed by `isolate` stamping the token
itself. And the token stays `v: 1`: the field is optional on read and every reader builds the
token field by field, so a token from an older build parses as not live, which costs at worst
one recovery prompt nobody needed.

**Residual risk, unchanged by this fix:** `recoveryToken` only re-reads the store when
`recoveryEpoch` bumps, so window B's picture of window A goes stale the moment A finishes.
That was already true of `recoveryPending` and is not made worse here; the honest fix is for
the recovery read to be driven by something that changes when the other window acts.

### M3 — The lock's compare-and-swap is not actually per-session — **fixed** (`80752e7`)

`src/git/isolate.ts:284` sets `lockValue` to the HEAD commit sha. `acquireLock` is a genuine
atomic create-if-absent, so two sessions can never both hold the lock — that part is right.
But `releaseLock` (`src/git/isolate.ts:505`) compare-and-swaps on that *value*, and two
windows at the same HEAD compute the same one. The CAS that ADR 0002 D5 describes as making a
release unable to "clobber another owner" therefore does not distinguish owners at all.

Fix: use `sessionId` as the lock value. It is already unique, already in the token, and already
what the ref is conceptually naming. It also gives M2 the ownership check it needs — a window
can compare `readLock(repoRoot)` against the session it believes it owns. `RepoLockedError`
does not surface the value, and the fixtures only need *a* value, so the blast radius is small.

Fix applied, with one wrinkle the finding did not anticipate: a ref can only point at an
object, so `git update-ref refs/guide-reviewer/lock window-a` is `fatal: not a valid SHA1`.
The id therefore travels as a blob — `guide-reviewer-lock:<sessionId>`, written with
`hash-object -w` — and the ref points at that. Content addressing is what makes it work:
`releaseLock` and the ownership check recompute the value they compare against instead of
trusting the ref they are about to act on. `readLock` reports the owning session id, falling
back to the raw object name for a lock this extension did not write, so the stale-lock drill
(§6.3, `update-ref … HEAD` by hand) still reads as held. A token written by an older build
recorded the ref value itself, so `releaseLock` retries the compare-and-swap on the raw value
— still a CAS, just on the old shape. `RepoLockedError.lockValue` is now `.owner`.

Regression tests: *"will not let one window release another window's lock"* (two sessions,
one repository, one HEAD), *"records the owning session on the token and reports it on
refusal"*, and *"still reports a lock this extension did not write"*.

### M4 — No exit from a restore that can never verify — **fixed** (`12adf0c`)

`discardRecovery` existed in the model and was contributed by no command, so a blocked restore
pinned `recoveryPending` forever and `canStart` with it. Now
`guide-reviewer.discardRecovery` ("Forget Pending Restore"), which releases the machine as well
as the reminder and destroys nothing — the stash entry and both refs stay in git. Regression
test: *"lets the user forget a restore that cannot be completed"*.

### M5 — Cancel was hidden in every state you would need it — **fixed** (`12adf0c`)

`guide-reviewer.cancel` was gated on `guideReviewer.sessionActive`, which is
`sessionStatus() === 'active'` — false in `blocked`, in `error`, and in a `preflight` that
stalled. Added `isSessionOpen` (`!== 'idle'`) and a `guideReviewer.sessionOpen` context key.
The recovery commands got the converse treatment: `recoveryPending && !sessionActive`, so they
cannot be fired at a live session (this narrows M2 but does not close it — a second window's
`sessionActive` is false).

### M6 — A failed pre-flight modal parked the machine forever — **fixed** (`12adf0c`)

`src/ui/prompts.ts` — `startSession` waits on `take(preflightAnswer)`. If `ui.confirm` rejected,
nothing ever called `preflightAnswer`, so the machine stayed in `preflight`: Start disabled,
Cancel hidden (M5), no way back without a reload. A rejected modal now counts as a decline,
which the machine already handles cleanly by aborting the frame.

### M7 — A pending restore went invisible in a repository git refuses to start in — **fixed** (`6036e69`)

`recoveryToken` returned `null` whenever the capability was not `ok`, because the fail shape
carried no `repoRoot` to key the journal on. A repository that is mid-rebase — a very plausible
state to find after a crash — therefore stopped reporting the stash holding the user's work.
The comment on that computed calls this "the one failure this whole subsystem exists to
prevent."

`probeGit` now carries `repoRoot` on the failures it discovers *after* locating the repository
(`rebase-or-merge-in-progress`, `unborn-head`) and the journal lookup uses it. Refusing to start
is not a reason to refuse to look. Regression test: *"still finds a pending restore in a
repository git refuses to start in"*.

### M8 — Workspace trust was left at the default — **fixed** (`8177522`)

`package.json` declared no `capabilities`, so VS Code treated the extension as merely *limited*
in an untrusted folder and loaded it anyway. This extension shells out to git and rewrites the
working tree, and a repository's own config can make git execute arbitrary commands — the exact
case workspace trust exists for. Both `untrustedWorkspaces` and `virtualWorkspaces` are now
refused with a reason, asserted in `test/unit/contributions.test.ts`.

## Minor

### m1 — Recovery modal fired on tokens with nothing to recover — **fixed** (`12adf0c`)

`checkRecoveryOnActivate` tested `token !== null` rather than `isRecoverable(token)`. A token at
`planned` never touched the tree and one at `done` was already restored, so both raised a modal
claiming work had not been restored. False alarms about data loss are the one kind of noise this
product cannot afford.

### m2 — A notification button that dispatched to nothing — **fixed** (`12adf0c`)

`teardownSession` passed `['Show recovery commands']` to `ui.notify` and discarded the return
value, so the button did nothing. The model cannot open a VS Code view, which is why it could
never have worked from there. Removed; `useRestoreBlockNotice` now reveals the output channel
itself, where the literal git commands are already printed.

### m3 — Product promises a merge UI for a blocked restore; the code gives commands — *open*

P0 edge row 2 says *"surface 3-way merge UI link"*. `restoreFromToken` returns
`commands: recoveryCommands(token)` and the UI logs them. That is arguably better — the commands
are exact and copy-pasteable — but the spec and the implementation disagree and one of them
should move. My preference is to amend the spec and keep the commands.

### m4 — `UiPort.openReview` is dead — *open*

`src/model/ports.ts:24` declares it, `src/ui/ports.ts:87` implements it as a log line reading
*"reveal lands in Phase 5"*, and nothing calls it: `useReviewDocuments` drives `vscode.diff`
directly. Delete the port member and its three test stubs, or wire the diff through it. A port
the model never uses is a boundary that isn't one.

### m5 — `wrap` discipline at two VS Code callback edges — *open*

Both are reads-only today, so neither is a live bug, but they are the two places the skill's
"check after every await" rule is not satisfied:

- `src/ui/documents.ts:169` — `focusCurrentStep()` runs after `await openDiff(...)`, and
  `openDiff` awaits `commands.executeCommand` unwrapped, so the continuation is outside the
  frame. It only calls `peek`, on a computed the same composable keeps subscribed.
- `src/ui/documents.ts:131` — `workspace.onDidChangeTextDocument(...)` is a raw callback that
  calls `peek(reviewViewModel)` through `focusCurrentStep`.

Fix: `await wrap(commands.executeCommand(...))` and `wrap(...)` the document listener. Cheap,
and it stops the reasoning in the iteration log ("a cached snapshot rather than a W5 stale-frame
read") from being load-bearing.

### m6 — `version: 0.0.0`, and no `CHANGELOG.md` — *open*

`vsce package` succeeds and produces `guide-reviewer-0.0.0.vsix`, but `0.0.0` is not a version
to ship, and the Marketplace renders a Changelog tab that has nothing behind it. `bumpp` is
already wired as `nr release`.

## Checked and found clean

Recording these so the next reviewer does not re-derive them.

- **Reatom idioms.** Every atom, computed and action is named, including the per-file and
  per-session dynamic names (`session#${id}.file#${path}.revealText`). Async reads are
  `computed(async).extend(withAsyncData(...))`; mutations are `action(async).extend(withAsync(...))`
  with `withAbort('first-in-win')` where a second click must not race. Extension order is
  async-before-anything-else throughout. `.status()` is only read where `{ status: true }` was
  passed. Reactive reads are hoisted above the first `await` in every async computed, with the
  W5 rule spelled out in a comment at `repoStatus`. No `ctx.*`, no `reatomAsync`, no `onConnect`,
  no `effect` at module scope — the bridge composables are the feature boundary, which is the
  pattern the skill asks for.
- **`preflightAnswer` is not an identity action.** It looks like one (`(approved) => approved`),
  but it is the event channel `startSession` awaits with `take(...)`, and `take` needs an action.
  It forwards to no atom. Correct as written.
- **Import boundaries.** Enforced twice — lint plus `test/unit/import-boundaries.test.ts` over
  the source graph, so editing the lint config cannot quietly open a hole. `src/guide` is pure
  (no `vscode`, no `@reatom/core`, no `node:`), `src/git` has no Reatom and never reaches up into
  `model`/`ui`/`commands`, `src/model` has no `vscode` and no `node:`. Verified by reading the
  imports as well as trusting the test.
- **No exam-like UX.** No score, timer, streak, or comprehension gate anywhere. Tab past the last
  step is a no-op plus one dismissible "Review complete." with a Finish button
  (`src/commands/index.ts` `advance`). Rationale is one line and switchable off. `k/n` counts
  skipped stub steps rather than hiding them, which keeps the number honest. Shift+Tab is exact
  because the revealed set is a pure fold over the cursor, not an undo log.
- **Restore reaches every exit.** Finish, Cancel, `deactivate()` and the failed-start unwind all
  funnel into `restoreFromToken`, none of them passes an abort signal, and `deactivate` drains
  the restore before disposing the Reatom scope. `startFailed` correctly declines to undo an
  isolation it inherited, so a refused second Start cannot damage the running session.
- **Marketplace metadata otherwise.** `publisher`, `displayName`, `description`, `categories`,
  `keywords`, `repository`, `bugs`, `homepage`, `engines`, `icon` (320×320) all present and
  sensible; `vsce package` produces a 96 KB VSIX with the right eight files.
