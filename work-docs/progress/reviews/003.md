# Review 003 — Reviewer — 2026-08-07 — Phase 9 / P0-A5 (Finish-keep + commit handoff)

Scope: the Finish-keep slice as it stands **after** the Phase 7 blocker fixes —
`finishKeepFromToken` / `discardApplyWrites` / `finalize` in `src/git/isolate.ts`,
`finishApplyKeep` / `finishSession` / `cancelSession` / `cleanupBackups` / `refreshHeartbeat` in
`src/model/session.ts`, the `done-kept` / `finishing-keep` stages and `isRecoverable` in
`src/git/journal.ts`, `advance()` in `src/commands/index.ts`, `deactivate` in `src/index.ts`,
the Finish/cleanup contributions in `package.json`, and
`test/integration/apply-commit.test.ts`.

Normative: [ADR 0004](../../decisions/0004-apply-mode.md) D6/D7 · [plan.md](../plan.md) Phase 9
done-when and R-apply-2/3/9 · [test-matrix §9.2](../test-matrix.md) ·
[specs/product.md](../../specs/product.md) apply acceptance + P0 v0.2 edge rows · the
`reatom-review` skill · [review 002](./002.md), whose fixes are re-verified where Finish touches
them.

**Verdict: request fixes.** Two blockers. Both are consent failures rather than engine bugs:
**B1** turns a merge conflict into the sentence *"Apply complete. Finish keeps your changes so
you can commit."* and Finish then keeps — and stages — the conflict markers Tabthrough wrote.
**B2** makes closing the VS Code window run the destructive apply Cancel with none of the
confirmation ADR 0004 D6 requires, deleting files the user authored during the walk.

The keep mechanism itself is right, and so is every Phase 7 fix I re-checked. What is missing is
the half of R-apply-3 that is not the refs: after Finish the product tells the user how to
**destroy** the pre-session backup and never how to get it back, and the ADR's stated escape
hatch throws.

## Blocker

### B1 — A conflict is announced as "Apply complete", and Finish keeps the conflict markers

`src/commands/index.ts:85-97` plus the absence of any gate in `finishApplyKeep`
(`src/model/session.ts:665-709`).

`model.next()` returns `false` for six different reasons: the walk is over, `saveDocuments`
refused, `beginApply` refused, the engine `refused`, the engine hit a **conflict**, or
`applyGuideStep` threw. `advance()` distinguishes none of them:

```ts
const moved = await wrap(Promise.resolve(model.next()))
if (moved)
  return

if (model.mode === 'apply') {
  const answer = await wrap(window.showInformationMessage(
    'Apply complete. Finish keeps your changes so you can commit.',
    'Finish and Keep',
  ))
  if (answer === 'Finish and Keep')
    await wrap(finishSession())
```

So the Tab press that just produced `<<<<<<< current` markers is answered with "Apply
complete" and a **Finish and Keep** button. And Finish takes it — nothing in
`finishApplyKeep` or `finishKeepFromToken` looks at the tree before keeping it, even though
`hasConflictMarkers` already exists in `src/git/apply.ts` and the engine itself refuses to
re-merge over markers.

Verified. Two-file commit, apply mode, a messy edit on the next step's file, one Tab, then
`finishSession()`:

```
PROBE A moved = false status = active
PROBE A markers on disk = true
PROBE A after finish status = idle
PROBE A markers still on disk = true
PROBE A token stage = done-kept
PROBE A index status = M  src/service.ts
PROBE A notifications = [
  "Conflict applying step onto your edits in src/service.ts. Resolve the markers in that file, then press Tab to continue.",
  "Could not return HEAD to main while keeping your changes. error: Your local changes ... Aborting
   Your applied changes are still in the working tree (kept). Stay detached and commit from here, ..."
]
```

The end state: a detached HEAD, a **staged** file full of conflict markers, a `done-kept`
journal, and an offer to open Source Control. The carry failed *because* of the markers — they
make the content differ from the branch tip — so R-apply-2's detached-keep path fires for a
reason that is not R-apply-2, and its copy ("commit from here") is advice to commit the markers.

This also defeats review 002 B3's own fix. Conflict deliberately stays `active` so Tab can
retry; the retry press does call `next()` first (correct), but every failed retry now also
raises the completion offer, so the user is invited to Finish on each attempt.

Fix, both halves:

1. Gate the completion offer on the model, not on a boolean: show it only when
   `!model.canAdvance()`. Better, have apply `next()`/`prev()` return a discriminated outcome
   (`'advanced' | 'complete' | 'conflict' | 'refused'`) so the command layer stops guessing —
   `steps.ts` already has the outcome in hand and throws it away.
2. `finishApplyKeep` must refuse when any step path still contains conflict markers, naming the
   file, before it checkpoints. `git status --porcelain` cannot see plain-text markers, which is
   exactly why the engine grew `hasConflictMarkers`; Finish needs the same check.

### B2 — `deactivate` runs the destructive apply Cancel without the ADR-required consent, and deletes files the user wrote during the walk

`src/index.ts:124` calls `cancelSession('deactivate')` on window close, reload, and extension
update. In apply mode that reaches `teardownSession` → `restoreFromToken` →
`discardApplyWrites` (`reset --hard` + scoped `clean -fd`) → stash-restore → `finalize`, which
deletes the after, backup **and applied** refs.

The confirmation ADR 0004 D6 requires — *"If `appliedIndex >= 0` or the applied checkpoint
differs from base, show a modal confirmation"* — is gated on `reason === 'cancel'`
(`src/model/session.ts:751`), so the one path the user does not think of as "discard my work" is
the one path that skips it.

Verified. Commit-entry apply session walked to completion, then one file authored by hand — the
mid-walk edit the product's *"User edits then abort"* row is about — then
`cancelSession('deactivate')`:

```
PROBE C my notes survive = false
PROBE C appliedRef      = null
PROBE C notifications   = ["Tabthrough restored your working tree before shutting down."]
```

`MY-NOTES.md` is gone, and there is no copy of it anywhere: it postdates the last applied
checkpoint, and `finalize` deleted that checkpoint regardless. Product spec's v0.2 bar is
*"**Zero** data-loss in apply mode (same bar as v0.1)"*, and this is a keystroke every user
performs daily.

Fix: `deactivate` must not restore an apply session. The durable journal is the whole reason
`deactivate` is allowed to be truncated — its own docblock says *"a truncated deactivate is
safe — the journal on disk is what the next activation reads"* — and Phase 10 already owns the
**Restore | Resume | Inspect** prompt that should meet this token on the next activation.
Leaving the tree exactly as the user left it is the honest half-state; restoring it silently is
not. Narrowest form: in `cancelSession`, return early when `reason === 'deactivate'` and
`model?.mode === 'apply'`, leaving stage `reviewing` for recovery. Read-only `deactivate` is
unchanged and still covered by the lifecycle suite.

See also [M1](#m1--discardapplywrites-deletes-untracked-files-the-user-authored-during-the-walk),
which is why the loss is total rather than recoverable, and applies to explicit Cancel too.

## Major

### M1 — `discardApplyWrites` deletes untracked files the user authored during the walk

`src/git/isolate.ts:463-507`. Review 002 B1 correctly replaced a bare `git clean -fd` with a
pathspec-scoped one. The scope predicate is the problem:

```ts
const toRemove = status.untracked.filter(path =>
  headPaths.has(path) || !afterPaths.has(path),
)
```

`!afterPaths.has(path)` means "absent from the pre-session capture", and the docblock calls that
*"mid-walk junk"*. But every file the **user** creates during an apply walk is absent from the
pre-session capture. Their new test file, their scratch notes, a file they extracted while
working through a step — all classified as junk and removed. Verified as part of probe C above.

The predicate should be "this session wrote it", not "it is new". The session knows exactly
which paths it wrote: the step paths, and the delta between the `applied` checkpoint tree and
the capture. Anything else must stay on disk even at the cost of a blocked restore — a restore
that stops and explains is always better than one that deletes.

While here: `finalize` deletes `appliedRef` on a verified Cancel (review 002 M4's fix, correct
per D6) — but it is also the last copy of the walk. Deleting it *after* a verified restore of
the pre-session tree is defensible; doing so on a `deactivate` the user never consented to is
what makes B2 unrecoverable.

### M2 — After Finish, the product explains how to destroy the pre-session backup and never how to restore it — and the documented restore path throws

Three pieces of one gap, all on R-apply-3 (Critical impact in the register).

**The kept message points only at destruction.** `src/git/isolate.ts:716-718`:

> `Pre-session backup refs remain until you run Clean Up Backups — Cancel is no longer the restore path.`

That is the only sentence the user gets about their stashed WIP, and it names the command that
removes it.

**"Clean Up Backups" has no confirmation and no disclosure.** `cleanupBackups`
(`src/model/session.ts:396-409`) deletes every ref under `refs/tabthrough` and clears the
`done-kept` token; `package.json` gates it on `tabthrough.gitUsable` alone; the command layer's
only message is *"Removed N Tabthrough backup refs."* ADR 0004 D6 permits deletion only when
*"the user explicitly confirms cleanup after Finish"* — invoking a palette entry titled "Clean
Up Backups" is not a disclosure that a stash of their uncommitted work is inside it.

The mitigating fact, verified, is that the stash **entry** survives, so the work is not
destroyed:

```
PROBE E stash list after finish  = "stash@{0}: On main: tabthrough:entry-session"
PROBE E cleanup removed         = ["refs/.../after/…","refs/.../applied/…","refs/.../backup/…"]
PROBE E stash list after cleanup = "stash@{0}: On main: tabthrough:entry-session"
```

But the token that named that stash message is cleared in the same action, so nothing in the
product can point at it afterwards.

**The ADR's escape hatch does not exist and throws if reached.** D6 says *"recovery command can
still restore pre-session **over** the kept tree only with an explicit dangerous confirm"*.
`tabthrough.restoreBackup`'s enablement is `tabthrough.recoveryPending`, which `isRecoverable`
makes `false` for `done-kept` — correct for the crash prompt, but it also removes the only route
back. And if the action is reached anyway, `restoreFromToken`'s first statement is
`advanceStage(store, token, 'restoring')`, and `LEGAL_STAGES['done-kept']` is `[]`:

```
PROBE B stage = done-kept
PROBE B recoverBackup threw = IllegalStageError
```

`guard` in `src/commands/index.ts` swallows that into the output channel, so the user sees
nothing at all.

Fix: (a) a modal confirm on `cleanupBackups` that lists what will be deleted and says the
pre-session stash is among it; (b) put the stash message and `git stash apply <backupRef>` in
the Finish message, so the restore route survives the token; (c) either implement D6's dangerous
confirm (Phase 10 task 10-d) or make `recoverBackup` refuse `done-kept` with that message
instead of throwing.

### M3 — The next Start silently overwrites the `done-kept` token

`isolate` writes the new token with `store.writeToken(token)`, keyed on `repoKey(repoRoot)`, and
`startSession` only refuses on `isRecoverable` — which `done-kept` is deliberately not
(`src/git/journal.ts:184-189`). So the first Start after a Finish erases the record naming the
previous session's stash message, backup ref and applied ref. ADR 0004 D6's "never clear the
token unless verified restore or confirmed cleanup" is broken by an ordinary Start.

The refs themselves survive and `listGuideRefs` still finds them, so this is a lost *pointer*,
not lost work — but it is the pointer M2 depends on. Fix: keep terminal `done-kept` records
outside the single-slot key (a small `keptSessions` list in the store), or surface the
outstanding kept session once before overwriting it.

### M4 — Finish stages the entire tree with `git add -A` and never unstages it

`src/git/isolate.ts:687`. To make the carry checkout succeed when the applied content already
equals the branch tip, Finish runs `git add -A` against the **real** index. Nothing reverts it,
and nothing disclosed it: ADR 0004 D3 says apply flattens into the working tree as *"ordinary
unstaged (and new) files"*, and the pre-flight repeats that. Verified on both the carry-success
and carry-failure paths:

```
PROBE D status --porcelain = "M  src/hello.ts"     (carry failed, still fully staged)
PROBE A index status       = "M  src/service.ts"
```

When the carry fails the user is left detached with a wholly staged index they did not ask for,
including any of their own mid-walk work that `add -A` swept up. Fix: attempt the plain
`checkout` first and stage only if git refuses; on carry failure, restore the index to what it
was (`git reset` to the checkpoint's parent state) or say plainly in the message that everything
is now staged.

### M5 — A crash during the carry turns Finish into Cancel, and the recovery copy says so in the wrong words

`finishing-keep` is `isRecoverable`, and `LEGAL_STAGES['finishing-keep']` includes `restoring`.
So a crash inside the three git commands between `advanceStage(…, 'finishing-keep')` and
`advanceStage(…, 'done-kept')` leaves a token whose next activation raises
`describeRecoveryPrompt`'s *"Tabthrough did not finish restoring your work last time."* with
**Restore now** offered — and accepting it runs `discardApplyWrites` and throws away the tree
the user asked to keep.

The window is small and Phase 10 owns the stage matrix (test-matrix §9.2/§9.3 both list it as
unwritten), so this is not a blocker. Two things should still change now: the recovery prompt
must special-case `finishing-keep` (the user asked to *keep*, not to restore — offer "Finish
keeping" or "Inspect" first), and the crash row must be in Phase 10's gate before the stage can
be considered shipped.

### M6 — Finish has none of the pre-checks the walk enforces on every Tab

`applyGuideStep` refuses on `status.unmerged`, refuses on conflict markers, and reports drift
before it writes a byte. `finishApplyKeep` — the action that ends the session by making the tree
permanent — checks nothing: not unmerged index entries, not markers ([B1](#b1--a-conflict-is-announced-as-apply-complete-and-finish-keeps-the-conflict-markers)),
not drift, not `appliedIndex`. The one place a bad tree becomes the user's problem forever is the
one place with no gate. Fix: reuse the engine's refusals as a Finish pre-check and surface them
the way Tab does.

### M7 — `IsolationHandle.token` is still mutable state outside the graph, and Finish is now a third writer

Review 002 M6, still open (`src/git/isolate.ts:289`), and Finish makes it load-bearing:
`finishApplyKeep` reads `handle.token` (`session.ts:666`), hands it to `finishKeepFromToken`, and
writes the result back (`session.ts:684`) alongside the two writers in `src/model/steps.ts`. The
`reatom-review` rule is *"mutable fields inside dynamic objects should be atomized"*, and the
concrete failure mode here is not aesthetic: if any apply error path skips its
`init.handle.token = outcome.token`, Finish checkpoints and journals from a token whose
`appliedRef` / `appliedIndex` are behind reality, while the UI shows the atom's value. Fix as
002 M6 described — one `isolationToken` atom, one writer, `appliedIndex` a `computed` over it.

## Minor

### m1 — `LEGAL_TRANSITIONS` grew two edges that nothing uses

`restoring → active` and `blocked → active` are both permitted (`src/model/session.ts:107-108`)
and neither has a caller — I grepped every `sessionStatus.to(...)`. They were added for review
002 B3/M7, both of which were then fixed a different (better) way: conflict stays `active`, and
`finishApplyKeep`'s blocked branch goes to `blocked`. The table *is* the safety guarantee, and
it now permits "abandon an in-flight restore and go back to reviewing". `session-status.test.ts`
asserts all 49 pairs *against the table*, so it followed the widening rather than constraining
it. Drop both edges.

### m2 — The applied checkpoint is implemented twice

`finishKeepFromToken` (`isolate.ts:648-665`) hand-rolls `writeWorkingTree` → `commit-tree -p
HEAD` → `writeRef` with an inline copy of the author/committer env, duplicating the exported
`writeAppliedCheckpoint` in `src/git/apply.ts:166-180`. Two implementations of one contract, one
of which has the `IDENTITY` constant. Call the exported one.

### m3 — Finish saves only step paths, not what the user wrote

`finishApplyKeep` flushes `model.guide.steps.map(step => step.path)`. ADR 0004 D6 step 1 says
*"flush saves for dirty buffers in the session's touched set"*, and in apply mode the touched set
includes the user's own files. The checkpoint (`add -A` over the on-disk state) and the carry's
`add -A` both then record stale bytes for an unsaved buffer. VS Code keeps the buffer, so
nothing is lost — but the committed-looking state and the editor disagree.

### m4 — "Finish Review" is the palette label in both modes

`package.json` gives `tabthrough.finish` one title, and `contributions.test.ts` pins it. The
status bar and pre-flight both say Finish keeps, so the copy is honest where the user is
looking; the palette is not. Worth a second command (or a `when`-scoped menu entry) reading
"Finish and Keep Changes" for apply, given how much of D6 is about Finish never reading as
Cancel.

### m5 — Nothing asserts that Finish creates no commit

The strongest claim in this slice — *never a silent `git commit`* — is checked only by
`harness.scmOpened === 1`. One `git rev-list --count HEAD` before and after Finish would close
it permanently. (I checked by hand: no commit is created. `commit-tree` writes an unreferenced
checkpoint object, which is not a commit on any branch.)

## Checked and found clean

Recording these so the next reviewer does not re-derive them.

- **Finish genuinely never stash-restores** (R-apply-9). `finishKeepFromToken` has no
  `stashApply` call and does not reach `finalize`; the backup ref and the stash entry both
  survive, verified in probe E. `finishSession` forks on `model.mode` before `teardownSession`,
  so the read-only Finish path is untouched.
- **`done-kept` is a correct terminal stage.** `LEGAL_STAGES` reaches it only from
  `finishing-keep`, it has no outgoing edges, `isRecoverable` excludes it so no false crash
  prompt fires and Start is not blocked, and `parseToken` still round-trips at `v: 1`.
- **Journal order across Finish is right.** Checkpoint and `appliedRef` are written *before*
  `finishing-keep`; the lock is released and the token persisted before `done-kept`; a
  checkpoint failure returns `blocked` without advancing the stage at all.
- **The carry never uses `-f`.** Both branches are plain `checkout` / `checkout --detach`, and
  the failure path keeps every ref and stays detached (R-apply-2), verified by the existing test
  and by probe D.
- **Review 002's Phase 7 fixes hold.** Conflict stays `active` and a second Tab refuses on
  markers rather than nesting them (re-verified in probe A); `finally { endApply }` plus
  `cancelSession`'s `applyPending()` guard keep Cancel reachable from a stuck `applying`;
  `finalize` deletes `appliedRef` and `for-each-ref refs/tabthrough` is empty after a verified
  Cancel; the heartbeat now beats through `applying` and `blocked`; `ui.applyPending` is a real
  Reatom computed bound with `useAtomRef`; `reviewViewModel` returns `null` in apply mode and the
  `tabthrough:`-scheme bindings carry `sessionMode != 'apply'`.
- **Reatom idioms in the Finish path.** `finishApplyKeep` is an `action(async)` with
  `withAsync()`, `finishSession` adds `withAbort('first-in-win')`, every git and port boundary is
  `await wrap(...)`, reads inside the action use `peek`, and no `.then` callback touches state.
  Everything is named. No `context.reset()` under `src/`. No stale v3 API. `cleanupBackups` is
  `withAsync({ status: true })` + `withAbort('first-in-win')`, which is the right pair for a
  destructive command reachable from the palette.
- **`commitHandoff` is a one-line SCM focus** and no code path anywhere constructs a `git commit`
  invocation (grepped).
- **The `done-kept` token does not block a later session** and `cleanupBackups` refuses while a
  recoverable token is outstanding, so cleanup cannot race a live review.

One timing artefact, not a finding: `recoveryPending` reads `recoveryToken.data()`, so for one
microtask after Finish it still reports the pre-Finish token and `cleanupBackups` throws
`RecoveryPendingError`. Reachable only by calling both in the same tick, which is why
`apply-commit.test.ts` awaits `recoveryToken()` first. In the bridge the computed is subscribed
and settles before any user click.

## Test gaps

### T1 — §9.2 coverage vs what exists

`apply-commit.test.ts` is six tests and covers the happy paths well. Against test-matrix §9.2:

| §9.2 row | State |
|----------|-------|
| Apply Cancel — sacred restore + confirm | **Covered** (also in the sacred suite now) |
| Apply Finish — tree kept, backup not applied, `done-kept` | **Covered** |
| Finish vs Cancel fingerprints distinct | **Covered** |
| Finish carry-checkout fails | **Covered** — asserts detached and warned; does **not** assert the index (M4) |
| Commit handoff | **Partial** — `scmOpened === 1`; nothing proves no commit was created (m5) |
| Readonly Finish still restores | **Covered** (lifecycle suite) |
| After Finish, cleanup retains then removes refs | **Covered** |

Missing, in the order I would write them:

1. **Finish after a conflict** — B1. Highest value: it is a two-line test and it fails today.
2. **`deactivate` in apply mode** — B2. The lifecycle suite's `deactivate` row is read-only only.
3. **A file the user authored during the walk survives** — M1. Assert it across Cancel *and*
   `deactivate`.
4. **`finishKeepFromToken`'s `blocked` branch** — the fix that closed review 002 M7 has no test
   at all. Inject a failing `exec` (the seam exists) so the checkpoint fails, then assert status
   `blocked`, Cancel still reachable, refs intact.
5. **Finish on an incomplete walk** — both current Finish tests are either a full walk or the
   single auto-advanced step. Stopping at step 2 of 6 is the ownership scenario.
6. **Working-tree-entry Finish** — `finishKeepFromToken` is entry-agnostic and both tests are
   commit-entry, yet the WT entry is the case where the pre-session WIP is *genuinely* orphaned,
   which is R-apply-3's actual scenario. Phase 8 owns the walk; this Finish row does not need it.
7. **Start after `done-kept`** — M3, and `restoreBackup` after `done-kept` — M2.
8. **Finish with an unsaved buffer** (`saved.ok === false` → warn, no Finish). The harness port
   always returns `ok`, so that branch has never executed. Same gap as review 002's T1 row.

1. **B1** — completion offer gated on `canAdvance()`; Finish refuses conflict markers.
2. **B2** — `deactivate` does not restore an apply session.

4. **M2** — confirm on Clean Up Backups; the Finish message carries the restore route.
